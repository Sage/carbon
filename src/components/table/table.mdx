## Draggable

Use `isDraggable` when users need to reorder rows. The drag handle is placed in the leftmost column and a row can be moved to the position of another row.

Dragging must not be the only way to reorder content. Provide equivalent keyboard-accessible actions, such as **Move up** and **Move down**, in the row's action menu. Both interactions should update the same source of row-order state.

<Canvas of={TableStories.Draggable} />

## Selectable

Use a checkbox to select a row. Reflect the selection in both the checkbox (`checked`) and row styling (`isSelected`).

`Links` and `Pills` within a selected row should use their inverse appearance where necessary to maintain sufficient contrast.

<Canvas of={TableStories.Selectable} />

## Expandable

Expandable rows are intended for `medium` and `large` tables and support one level of child rows. The expansion control is placed in the leftmost cell, the rest of the row is not clickable.

The control is keyboard operable: **Enter** or **Space** expands and collapses the row.

<Canvas of={TableStories.Expandable} />

## Sticky columns

Use sticky columns to retain important context while the table scrolls horizontally. The component supports locking one column on each side and retains a shadow between sticky and scrolling cells.

Horizontal scrolling applies to the whole table, including its sticky columns, and uses the browser's native scrollbar.

<Canvas of={TableStories.StickyColumns} />

## Sticky rows

Use a sticky `header` to keep column headings visible while users move through longer tables. The vertical scrolling relies on the viewport so that it works on mobile screens as well.

Although `stickyRow` supports a `footer` or `both` rows for specialist cases, the recommended pattern is a sticky header only. Avoid sticky footers and internally scrolling tables where possible, as they can introduce nested scrolling regions that are difficult for keyboard and screen-reader users to navigate.
