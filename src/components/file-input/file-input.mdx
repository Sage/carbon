### Accept and file type validation

The `accept` prop is passed directly to the underlying HTML `<input type="file">` element, and helps guide users towards uploading files of the correct format or type.
Please see the [MDN docs](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/accept) for more details on this attribute. When selecting a file via the
"select file" button, the operating system's file picker will either highlight the appropriate files, or make it impossible to select incorrect ones.

Note that `accept` does not prevent the user from uploading a file of the incorrect type via drag and drop, so you should still use the `onChange` prop to add an error
message as soon as an inappropriate file is added - as shown below. And of course nothing takes away the need for validation on the server side.

<Canvas of={FileInputStories.FileTypeValidation} />

### Single file vs multiple files

By default FileInput only accepts a single file (`multiple` defaults to `false`): the native input's picker restricts selection to one file, while the
drop zone remains available alongside its status card so the user can select a replacement. The default instruction explicitly offers both options:
drag and drop, or click the Select files button. If you supply `buttonText`, the default instruction uses that label; supply `dragAndDropText` to
replace the instruction entirely.

Set `multiple={true}` (or just `multiple`) when more than one file should be selectable. The drop zone is always visible alongside file status cards,
so users can keep adding files.

Dragging and dropping bypasses the native picker's restriction, so more than one file can still reach `onChange` even with the single-file default.
FileInput never discards files or derives `error` on your behalf (the same rule that applies to a required field with no files), so your `onChange`
should check `files.length` and set `error` yourself when it's greater than one - the example below does exactly that, showing the same Field-error
treatment either for a missing required file or for too many files being dropped at once.

<Canvas of={FileInputStories.SingleFile} />

### Tracking upload status

The `uploadStatus` prop is used to indicate when a file has been added, as well as to display the current status or progress of its upload —
including options to cancel or remove the uploaded file. You must provide this prop (as a `FileUploadStatusProps` object) in order for users
to see any visual indication of the uploaded file.

The drop zone remains available while statuses are displayed in both single- and multi-file mode. Consumers own the status array and append, update,
or remove entries as the upload lifecycle changes.

For this reason the `onChange` function prop is mandatory - without providing an implementation for this event handler that updates the
components `uploadStatus`, there will be no visual change once a file has been added to the input.

#### Client side example

Here is a relatively simple example of using a [FileReader](https://developer.mozilla.org/en-US/docs/Web/API/FileReader) to track progress purely
on the client side, resulting in storing the file locally as a `data:` URL. This is a way to show users a preview of their file if you do not intend
to track upload progress on the server, or do not actually send the files to a server until form submission.

Note the use of a `ref` to store the `FileReader` object - this is not essential but avoids having to create a new `FileReader` object more than once in the
lifecycle of the component.

This example also contains validation to restrict the user from uploading large files - this is useful because storing a large file in memory may make the
browser freeze or even crash. If your application needs to process large files on the client side then consider
[reading the file into an ArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/API/FileReader/readAsArrayBuffer) and processing that piece-by-piece.

#### Uploading with a progress percentage

With `progress` set, the status icon exposes a `progressbar` role with `aria-valuemin`,
`aria-valuemax`, and `aria-valuenow` set to the percentage, so assistive technology announces the
exact figure as it updates. `progress` alone only drives the ring loader's fill though - it isn't
turned into visible text on its own, so pair it with a `message` (e.g. `"Loaded 56%"`) if you want
the percentage shown as a label too.

The same example above (`UploadStatusTracked`) starts with exactly that - a static "Loaded 56%"
card - so a tracked, in-progress state is visible right away, rather than only once you drop a file
yourself (for a small file, the browser may fire so few progress events that it jumps straight to
"completed"). Cancel clears it, or drop a real file to see the FileReader-driven version take over.

<Canvas of={FileInputStories.UploadStatusTracked} />

#### Uploading without a progress percentage

Without `progress`, there's no percentage to report at all - the icon renders the same ring loader
but spins indefinitely to indicate an indeterminate upload, and its accessible label falls back to
the status message instead (either your own `message`, or the localized default,
`fileInput.uploading`).

The example below - the same `UploadStatusUntracked` story used for "Upload status (Untracked)"

- uses this indeterminate, no-`progress` form: it sets `label="Upload status example"` but omits
  `message`, so the default locale text ("Uploading…") is the status message a screen reader
  announces, alongside `aria-label={filename}`. Cancel is wired to clear the status, so the drop zone
  returns afterwards.

<Canvas of={FileInputStories.UploadStatusUntracked} />

#### Showing a thumbnail

Supplying `thumbnailSrc` on a status object (any status - uploading, completed, error, or previously
uploaded) adds a leading thumbnail column ahead of the filename, in place of the compact inline status
icon shown otherwise. `SingleFile` and `MultipleFiles` above demonstrate this too, once you upload a real
image, but this example shows the with-thumbnail File card layout without needing to upload anything.

<Canvas of={FileInputStories.WithThumbnail} />

## Props

### File Input

<ArgTypes of={FileInputStories} />

Props for `uploadStatus` are discriminated by `status`. Use `onCancel` for uploading, `onDelete` for completed files, and `onRemove` plus optional `onRetry` for failures. The deprecated `onAction` remains a primary-action fallback. Previously uploaded files are read-only and accept none of these callbacks. Completed and previous files accept optional `href`; filenames remain text. Every status accepts an optional decorative `thumbnailSrc`.

#### Migrating status props

- Remove `onAction` from `status: "previously"` values; previously uploaded files are read-only.
- Use `href` to provide the Preview link for completed and previously uploaded files.
- Remove `download`; it is no longer accepted in file-status props.
